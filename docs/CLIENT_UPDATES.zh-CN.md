# 客户端构建与自动更新

## 用户安装什么

更新通道现已推进至 [0.1.28](https://github.com/wanghao9103/farsail/releases/tag/client-v0.1.28)，由[正式工作流](https://github.com/wanghao9103/farsail/actions/runs/39365699777)从 `11a75bbfe5a49fd2665c98b34bb3d7c817cd255c` 构建。三平台签名包、原生安装检查和公开字节/签名核验通过，普通固定更新清单与版本附件及重建结果一致。本版增加远控一次批准后的文件复制粘贴。两端均需更新，打开**共享与设置 → 软件更新 → 检查更新**，结束连接后安装。物理双机文件粘贴仍待验收。

GitHub Actions 构建 Windows x64 NSIS 安装包，以及 Ubuntu x64、ARM64 Debian 包。发布成功后，三种安装包都会放到对应版本的客户端 Release；Actions 附件只是临时构建产物，不是更新通道。旧客户端没有更新器，需要手动安装一次首个支持更新的版本。服务端升级包不会升级桌面应用。

“共享与设置”的“软件更新”显示当前版本、检查结果和下载进度。默认开启自动检查：正式安装版在启动后稍等片刻检查，之后每小时检查一次。自动下载与安装可以选择开启；有远程会话或查看窗口时，会等待结束后再安装并重启。Windows 沿用当前用户安装方式。设置会保留到下次启动。开发版不自动检查公网更新通道。

更新通道为 [client-updates](https://github.com/wanghao9103/farsail/releases/tag/client-updates)，清单附件是 `latest.json`。2026-10-10 已公开 [0.1.21 签名版本](https://github.com/wanghao9103/farsail/releases/tag/client-v0.1.21) 与更新清单，包含 Windows x64、Ubuntu x64 和 Ubuntu ARM64；GitHub Actions 完成三平台构建、原生检查、签名与公开下载校验后推进通道。Ubuntu 24.04 是 x64/ARM64 的 CI 构建基线，本地 x64 Ubuntu 26.04 构建不能代替 ARM64 验证。

2026-10-19，[正式签名发布工作流](https://github.com/wanghao9103/farsail/actions/runs/39199106307)及公开下载核验通过后，更新通道已推进到三平台 [0.1.22 签名版本](https://github.com/wanghao9103/farsail/releases/tag/client-v0.1.22)。已安装 0.1.20 或 0.1.21 的用户可打开“共享与设置 → 软件更新 → 检查更新”，下载后按提示安装。下文介绍的更新弹窗在升级到 0.1.22 后可用。

此前更新通道提供 [0.1.23 签名版本](https://github.com/wanghao9103/farsail/releases/tag/client-v0.1.23)，由[正式发布工作流](https://github.com/wanghao9103/farsail/actions/runs/39208981511)从 `c217f20823e864ccd2d76bf19f29ad9ccd377309` 构建。三平台安装包、签名及公开下载核验通过，固定更新通道清单与版本附件一致。已有客户端可打开“共享与设置 → 软件更新 → 检查更新”，待进行中的连接结束后选择“安装更新”。

更新通道此前推进至 [0.1.24](https://github.com/wanghao9103/farsail/releases/tag/client-v0.1.24)，由[正式工作流](https://github.com/wanghao9103/farsail/actions/runs/39213734063)从 `c3ffb8aab093f2c3db4deeb98c7efcff97d9aa56` 构建。三平台原生/安装检查、公开包签名及摘要通过，普通固定更新地址与版本清单逐字一致。本次改善画面调度和有界流水发送，并移除画面悬停提示；两端都应升级后比较实际效果。30 FPS 是调度目标，不是用户游戏现场实测值。

0.1.23 将屏幕共享与文件接收统一为**允许远程连接**，保存开关选择并按平台启用能力。关闭主窗口后通过托盘/任务栏继续运行，手动安装前应从托盘选择“退出 FarSail”或从窗口菜单选择“退出”。Windows 启动时通过系统 UAC 申请管理员权限，取消则取消本次启动；安装器仍采用当前用户模式。Windows CI 已验证嵌入清单、实际提权进程、托盘关闭/恢复及 NSIS `/UPDATE /R` 重启；交互式 UAC 确认/取消与真实已安装客户端跨版本更新仍未验证。当前行为见[文件传输](FILES.zh-CN.md)。

ARM64 系统名为 `aarch64`，Debian 包名后缀为 `arm64.deb`，清单目标是 `linux-aarch64-deb`。x64 保留 `linux-x86_64-deb`，Windows 保留 `windows-x86_64-nsis`。客户端按本机构建架构精确选择条目，并校验下载包名；ARM64 遇到缺少 ARM64 条目的旧清单时，会显示没有兼容更新，不退到 amd64。安装和架构查询见[Ubuntu 客户端](UBUNTU_INSTALL.zh-CN.md)。

原生 ARM64 CI 使用 GitHub 官方[托管 runner](https://docs.github.com/en/actions/how-tos/write-workflows/choose-where-workflows-run/choose-the-runner-for-a-job)，不把 x64 构建或 QEMU 可用当作 ARM 原生运行证据。

更新通道此前推进至 [0.1.27](https://github.com/wanghao9103/farsail/releases/tag/client-v0.1.27)，由[正式工作流](https://github.com/wanghao9103/farsail/actions/runs/39233924894)从 `bca87a13e4ea246e0a5e5eed5ade4221d4c781ba` 构建。三平台原生/安装检查、公开包签名和摘要通过，普通固定更新地址与版本清单逐字一致。两个 Linux 架构的真实签名助手沙箱及包内权限检查通过；真实桌面认证、系统重启后的授权保留和受管理系统策略仍待现场验证。

## 0.1.22 的更新弹窗

0.1.22 新增以下更新弹窗与交互行为，同时精简桌面各页文案并优化布局。

发现新版本后，会在没有远程屏幕或文件连接、其他原生窗口或其他弹窗时显示“软件更新”窗口。正在处理操作、保留连接或注册邀请，以及注册、验证邮箱或找回密码期间，自动提醒也会延后。同一版本在每次运行期间最多自动提醒一次，重新启动客户端后可以再次提醒；这不依赖鼠标键盘的空闲时长。

点击“稍后”关闭窗口，本次运行不再自动提醒该版本。如果此前已经开启自动下载与安装，关闭操作显示为“后台更新”；开始安装后显示为“关闭窗口”。关闭弹窗不会改变任何更新偏好，也不会取消已经开始的下载或安装。顶部更新通知及“软件更新”设置中的“查看更新”都可以手动重新打开弹窗。

下载、下载进度、失败后重试以及“安装更新”集中在弹窗内。无法确定总大小时，显示已下载量，不显示百分比。未开启自动安装时，“立即更新”先下载并验证安装包，之后需点击“安装更新”。若仍有远程屏幕或文件连接、其他原生窗口，安装会等待；结束这些活动后，请再次点击“安装更新”。已开启自动安装时，客户端会自动重试等待中的安装。

自动检查控制定时发现版本，自动下载与安装控制已发现更新的处理方式。开启自动下载与安装时，也会开启自动检查；之后单独关闭自动检查，不会取消已发现更新的自动处理。发现版本、打开或关闭弹窗均不会开启任何更新偏好。设置会保留到下次启动；设置内容无法解析时，两项自动设置均关闭，不会自动开启。

## Ubuntu 更新授权

0.1.27 删除重复的更新说明，将失败转换为简短、可操作的提示，不在更新窗口展示原生诊断信息。Debian 包安装 root 所有的专用助手与独立 Polkit 动作。首次成功的应用内更新为当前调用账号保存后续 FarSail 签名更新授权；通过旧版 pkexec 更新器升级时复用本次安装授权。无法确定调用账号的手动安装，则在首次应用内更新时授权。

规则只匹配同一账号活动本地会话中专用助手的安装动作。助手独立核验内置发布公钥、签名版本、包名与本机架构，拒绝同版或降级，将安装包复制到 root 所有的目录后才调用 dpkg。输入为标准输入中的签名与包内容，不接受任意文件路径或命令。升级保留授权，卸载撤销授权。也可单独撤销：

```bash
pkexec /usr/libexec/farsail-update-helper revoke
```

签名包沙箱验证签名拒绝、元数据与版本检查、账号规则匹配、显式撤销及软件包维护脚本，不修改宿主安装。它不能代替真实桌面认证、重启系统后的授权保留及受管理系统策略优先级验证。

## 维护者配置

应用内只保存更新公钥。将对应私钥保存为 GitHub Actions 仓库 Secret `TAURI_SIGNING_PRIVATE_KEY`；工作流将 `TAURI_SIGNING_PRIVATE_KEY_PASSWORD` 设置为空字符串，以适配当前无密码签名密钥。请在仓库外安全备份私钥，不要提交、作为发布附件、写入日志或文档。丢失该密钥后，现有安装将无法接受新签名；不能直接用另一把密钥替换已安装客户端信任的密钥。

2026-10-10 已通过名称列表核对仓库存在该 Secret，并完成 0.1.20 与 0.1.21 云端签名发布；新维护环境应恢复匹配密钥，不要重新生成替代公钥。更新签名用于验证包内容和版本，与 Windows Authenticode 发布者证书是两件事，不会因此消除 SmartScreen 提示。

维护者不需要手动粘贴私钥：初始化脚本先检查本地私钥是否与应用内公钥匹配，再通过已经登录的 GitHub CLI 保存 Secret。值通过标准输入传递，不出现在命令参数或日志中；GitHub CLI 会在本地加密后上传。普通客户端用户始终无需配置签名 Secret。不带应用参数执行脚本时只做本地检查；下面的应用命令需要具有该仓库 Secrets 写入权限的账号。更换维护电脑时应恢复备份中匹配的私钥，不要重新生成替代密钥。本仓库已完成初始化；普通客户端用户不需要执行以下维护者命令。

```bash
gh auth login --hostname github.com
node scripts/configure-client-updates.mjs --apply
```

## 自动发布流程

修改 `apps/desktop/src-tauri/tauri.conf.json` 中的客户端版本，合入评审后的源码，再推送对应版本标签。下面是 0.1.21 发布所用的标签示例；该标签现已存在，不要重新创建或重定向。后续发布必须先递增应用版本并使用对应的新标签。

```bash
git tag client-v0.1.21
git push origin client-v0.1.21
```

也可以在 GitHub 网页上发布对应版本的客户端 Release，或在 Run workflow 中选择源码分支并填写对应版本标签。Run workflow 默认只构建签名候选；只有显式选择 `publish_release` 才公开版本并推进更新通道。标签及客户端 Release 事件仍按发布流程执行，维护者无需本地构建工具链。

`Client installers and signed updates` 工作流会自动构建三种架构目标。Windows 验证安装后的程序摘要与管理员清单、实际提权进程、原生设置、重启、远程偏好、托盘恢复、NSIS 更新重启、重装和卸载。Ubuntu 分别使用 `ubuntu-24.04` 和 `ubuntu-24.04-arm` 原生 runner，检查 WebKitGTK IPC、系统密钥环、包元数据、实际 ELF 架构和运行依赖；保持通用 ARM64 指令目标。上传前验证三份安装包的签名、签名中的版本、源码提交、摘要、Linux 架构及 Windows 安装报告。PR 构建不读取生产签名私钥，只提供预览附件。

版本 Release 保留不可覆盖的安装包、签名、校验文件和验证元数据。每个附件匿名公开下载后必须与已经测试的字节完全一致，才推进更新通道。通道不能倒退到更旧或相同版本，三种目标缺一不可：构建失败、缺少签名、安装验证失败都会保留旧通道。更新通道先上传待替换清单，再替换已有附件；替换期间短暂检查失败时，客户端保留当前安装。
