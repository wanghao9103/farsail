# FarSail authenticated transport (WI-003/004)

`crates/transport` uses encrypted QUIC from iroh / iroh-relay 1.2.0. The endpoint key is read directly from the Ed25519 private key the client already uses to register its device. The connection public keys must match the source/target public keys in the authorization record. The coordinator only provides restricted address discovery and grant validation; it does not forward application frames. The Tauri WebView receives only session state, selected path and RTT, and cannot read device keys, device tokens or grants.

<a id="使用流程"></a>

## Usage

1. The client logs in, binds its device and sends generation-bound heartbeats. `NativeClient::start_transport` retrieves the same device key from secure storage, binds an endpoint and publishes its `EndpointAddr` to the coordinator; addresses are updated after heartbeats. Port mapping and public-address lookup services are disabled by default. `TransportConfig` explicitly binds to `127.0.0.1:0` by default for local tests. Desktop settings allow a UDP bind address, a self-hosted HTTPS relay and forced relay.
2. The requester requests `view`, `control` or `files`, and the target explicitly approves. The target's native memory retains the grant that only it can obtain. After approval, the requester queries the peer address using its local device credential and heartbeat generation. The address returns only the other participating device in the session, and both devices, logins and leases must remain valid.
3. The requester establishes an iroh connection to the target's registered public key. The target validates the requester through the connection's authenticated public key before delivering the grant in an encrypted bidirectional stream; status polling cannot leak it. Using its own device credential, generation and grant, the requester asks the coordinator to validate the session ID, exact permission, both public keys, nonce and remaining TTL, then replies with nonce proof. The target opens data streams only after validating that reply. Each handshake step has a 10-second limit and each message a 4 KiB limit. The target handles at most 8 concurrent handshakes and caches at most 4096 session IDs to reject replays.
4. An authenticated `Session` provides `send(Frame)` / `receive()`, `permission()`, `path()`, `is_open()` and `close()`. The protocol-version byte is 1. Independent frame types are `Control`, `Media` and `File`, limited to 64 KiB, 1 MiB and 256 KiB respectively. `control` requires a `control` grant, `media` allows `view`/`control`, and `file` requires `files`. WI-004 integrates JPEG screen data and Windows system input with the first two; file contents/resume remain for WI-005.
5. Every 15 seconds, the target renews with the service and delivers a new grant over the authenticated connection; both sides revalidate about every 5 seconds. The remaining TTL returned by the service and the local `Instant` at the start of HTTP form a conservative cutoff, and an independent expiry task closes the connection. Revocation, disablement, unbinding, logout, heartbeat-generation changes, service unavailability or grant invalidation prohibit application frames beyond the local cutoff. A short window exists between the target rotating the token during renewal and the requester receiving the update. The requester may wait only for the update message and cannot extend the old lease.
6. Logout and local disconnection first close sessions and endpoints. Local grants for established sessions become invalid immediately, and server revocation is requested asynchronously on a best-effort basis. After restarting an endpoint, an old approval for the original session cannot be used to reconnect: a new request and approval are required. Valid approvals that have not yet been used are retained when starting an endpoint for the first time. Results of concurrent startup or connection attempts are written to the current session only if they match the native lifecycle generation; stale results are closed. The client retains at most 16 active sessions, removing them automatically after closure. If the coordinator is unreachable at disconnection, remote revocation waits for the short lease to expire; locally, old sessions are never allowed to continue.

Media-stream reads and writes use a 400 ms deadline. Incomplete media frames that time out or reset are discarded, while the next stream can still be processed. Control messages continue to be received, avoiding a stall on an expired large image. The Windows viewer returns an application-level sequence acknowledgment after receiving and validating each JPEG. The host permits only one unacknowledged image and stops streaming and closes the session if it is not acknowledged within 1 second. `tx.finish()` means only that the local write completed, not that the peer consumed it. Capture keeps only the latest frame, throttles JPEG payload with a 1.5 MB/s token bucket, retrieves the latest image again after waiting, and does not send images older than 700 ms. Actual link bytes include protocol headers and retransmissions. This policy applies to the current JPEG baseline. WI-006 must remeasure latency, frame drops and bandwidth when switching to video encoding. For the precise media and input byte contract, see [REMOTE.md](REMOTE.md).

`Session::verification_code()` derives the same short code on both sides from the QUIC/TLS exporter combined with the session ID, exact permission and both device public keys for manual verification. It neither uses nor displays the grant token. RTT refers only to the selected transport path.

<a id="路径和-relay"></a>

## Paths and relay

`Session::path()` reads iroh's current **selected path**, showing `direct`, `relay` or `connecting` and that path's RTT. Configuring a relay URL merely allows that server to be used; it does not prove that data actually passes through it. `force_relay` calls `clear_ip_transports()`. Local tests confirm that neither side has IP transport and the selected path is `relay`. Local tests bind to `127.0.0.1`, do not access the default public lookup or public relay, and do not modify the firewall. Relay URLs must use HTTPS with no credentials, query or fragment. The coordinator accepts only URLs in `FARSAIL_RELAY_URLS`; the client also refuses to dial a relay that differs from its local configuration. TLS uses standard certificate validation; local tests explicitly add a temporary certificate root, with no accept-all verifier.

Files sessions prefer a direct path: with known peer IP addresses and without forced relay, the requester gives an IP-only dial a three-second window before adding the configured relay address. The fallback dial has the existing ten-second connection limit; application authentication follows with its own bounded steps. Iroh may already know a peer's relay from a previous connection, so a connection using that cached path waits for direct upgrade during the remaining three-second window before file data is sent. If direct is unavailable, the verified relay connection is retained and can later recover a direct path. This reuses the current endpoint and device identity, preserves screen sessions, and does not route file bytes through coordinator APIs. View/Control dialing and explicit forced-relay settings retain their existing behavior. No known IP addresses means no direct-only wait. NAT reachability remains an environment-dependent condition, and the interface reports the actual selected path.

For a self-hosted server example, see [deploy/relay](../deploy/relay/README.md). A public IP can be used as the HTTPS hostname, but the certificate must match that IP. Public deployment, cross-NAT traversal rates, a second physical Windows computer, physical mobile devices and long-term link performance still await WI-008 verification.

## Address refresh without restart (P2P-019 / 0.1.9)

New outbound/inbound connections request full address discovery on the current endpoint. Authenticated relayed sessions check for retries every 30 seconds; an endpoint-level lock and 30-second cooldown combine concurrent requests. A watcher promptly publishes address changes. Uploads check the lifecycle and heartbeat generation and are serialized to prevent delayed old addresses from overwriting a new endpoint. Status polling does not trigger a network refresh, and direct sessions do not independently trigger periodic retries. Refresh neither rebuilds the endpoint nor clears approvals nor stops the screen; it is skipped when relay is forced or no relay is configured. The interface shows current relayed transport, a direct-connection attempt, periodic retries or forced relay. A successful refresh request does not mean successful QAD or hole punching.

Iroh 1.2.0 triggers a major/full network report by reinserting the configured relay unchanged. For focused validation of real loopback QAD failure → recovery, uninterrupted authenticated sessions, address generations and cooldown, see [P2P-019](verification/WI-P2P-019.md). Upgrading existing sessions across NAT still requires actual acceptance testing on two computers; direct connections are not guaranteed for every NAT.
