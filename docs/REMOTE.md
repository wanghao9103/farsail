# FarSail Windows remote viewing and input (WI-004)

The Windows host must log in, bind its device and start authenticated transport, then click “Enable local sharing” locally. Enabling sharing actually probes DXGI duplication for the current monitor, then updates `can_host=true` at the coordinator using the current heartbeat generation; initial binding remains false, while file capability is controlled by its independent local receiving switch. By default, the host must still explicitly approve every request. When local sharing is already enabled, “Remote standby” can be explicitly enabled to automatically approve viewing/control requests from the same account that the server has verified. Version 0.1.10 saves these two local choices in encrypted storage. After an ordinary restart, it revalidates the same service, account, device, login session, heartbeat, transport and interactive desktop, then restores sharing before standby. Manually disabling standby restores approval for each request; manually stopping sharing also remembers both choices as disabled. Logout or an identity change clears the preferences. Ordinary window closure or a temporary fault stops effective activity while retaining valid preferences. The requester then connects: `view` receives screen data only, while `control` can send system input. Local “Stop immediately”, disconnection, window closure, logout and lease invalidation all stop local streaming and input first, then attempt server-side authorization revocation.

## Media contract

The first usable screen path is the **JPEG baseline**: about 5 FPS, quality 55, fitted within 1280×720, with each JPEG limited to 1 MiB and a pixel budget of 2,073,600. `crates/windows` finds the DXGI adapter for the target monitor, maps each row using a D3D11 staging texture, and handles row pitch, DXGI rotation, negative coordinates and per-monitor DPI. It copies only in memory and never writes actual desktop frames to files or logs. `ACCESS_LOST`, the secure desktop or a mode change stops the current session and displays the reason. The user must return to the ordinary desktop, request/approve again, then connect.

`crates/media` uses the `FSM1` binary packet, containing: four-byte magic, a byte codec=1 (JPEG), `u32 monitor`, `u64 layout`, `u64 sequence`, `u64 captured_ms`, `u32 width/height` and `i32 origin_x/y`, all big-endian, followed by JPEG. Before decoding, it checks the length, pixel budget and JPEG's own dimensions rather than trusting the declared width and height alone. The monitor list is `FSL1` followed by JSON; the viewer selects a monitor using `FSS1` plus a big-endian `u32`. Switching monitors rebuilds capture and increments layout; mouse coordinates from old frames are rejected. Screen FPS is based on frames actually received. Network RTT is the selected QUIC path's RTT and does not equal screen latency. H.264/H.265, 4:4:4 and adaptive bitrate are reserved for WI-006.

The capture thread keeps only one latest-frame slot and skips encoding when DXGI has no new content or RGB matches the previous frame. Media writes and reads have a 400 ms deadline. A timeout/reset of a partial frame drops that frame and continues reading the next one. Each frame receives an application-level `FSA1` plus sequence-number acknowledgment, with a maximum wait of 2 seconds per attempt; only 3 consecutive failures close the session. The last frame of a static screen is also retried within bounds; duplicate frames are acknowledged without being displayed again. At most 3 bounded unacknowledged frames prevent unlimited backlog after QUIC's local `finish`. The sender throttles JPEG payload with a 1.5 MB/s token bucket, retrieves the latest frame again after waiting for budget and skips a new frame older than 700 ms. Retries may send the current last frame, subject to the 3-attempt limit above. This budget excludes QUIC/TLS/IP headers and retransmitted network bytes. Control reception and media sending run continuously and separately, so a bad image cannot occupy the input loop. Long-term public-network bandwidth and latency still require measurement on two computers.

## Input and permissions

The native layer parses allowlisted `Input`: movement in normalized coordinates; left or right button events with monitor/layout/coordinates; scrolling on both axes; permitted Windows VK key-down/key-up events; and Unicode text up to 64 characters. The viewer first calculates letterboxing from the actual image fitted to the window and sends 0–1 coordinates only within the image. The system maps them to physical pixels on that monitor, retaining negative coordinates. Buttons/scroll independently validate and move to their supplied position without relying on an earlier move message. Middle-button events, non-finite/out-of-range coordinates, stale layouts, extra JSON fields, unknown VKs and oversized messages are rejected.

Each control message has a consecutive sequence number. Local sending is serialized by a bounded lock and queue; mouse moves may be dropped when busy. The host can buffer 32 out-of-order inputs and wait at most 2 seconds for a missing sequence number. Duplicates, excessive gaps, continued missing input or exceeding the total limit close the session and release held keys. When high-frequency movement exceeds 120 messages per second, only moves are dropped, never key-up or release commands. Before input execution, the local sharing switch, session state and current layout are checked again while holding the same input lock. Stopping first clears the active flag, then acquires the lock and releases keys and mouse buttons injected by this session. Failed `SendInput` releases are retried and reported as incomplete cleanup. Viewer focus loss, the pointer leaving the screen and “Release keys” send a release command. The system secure desktop/UAC/a logged-out Windows session are unsupported, and privileges are not elevated to bypass Windows restrictions.

Both sides derive their verification code from the same QUIC/TLS connection's exporter, using `farsail/verify/v1` and the session ID, exact permission and both device public keys as context, then display a short code for manual comparison. Grants, device tokens, private keys and refresh credentials remain in Rust only. Binary frames received by the page are rendered through Tauri raw IPC and Blob JPEG; desktop frames are never placed in logs or long-term storage.

## Local execution and acceptance

Addition in 0.1.11: display/quality layout changes must not lose the UP event for an injected button. Only buttons owned by this session may be released. Missing/old layouts do not prevent release, while new DOWN events with old coordinates remain disallowed. The viewer's own pointer capture covers the end of a drag outside the image. Focus loss or unexpected capture loss releases and cancels input; moving into the image with a button already held outside does not create a new remote click. All execution still follows checks for valid authorization/sharing/session/input lock, and Windows refusals are not bypassed. See [INPUT-021](verification/WI-INPUT-021.md).

First follow the [client instructions](CLIENT.md) to start this project's PostgreSQL/Mailpit, coordinator and Tauri. Local two-endpoint integration tests use isolated accounts, temporary DPAPI directories and real PostgreSQL/Axum/iroh, and update host capability through the normal flow; the database is not manually modified. On a local machine with an interactive desktop, `scripts/test-remote.ps1 -RealCapture` additionally runs real DXGI → JPEG → authenticated connection → decoding; actual pixels always remain in memory. `cargo test -p farsail-windows real_input_into_own_foreground_window -- --ignored --nocapture` sends harmless text, key combinations and clicks only after the test's own window obtains foreground status and its foreground process is checked. If that check fails, the test fails before injection. CI has no interactive desktop and runs only synthetic-frame, coordinate/rotation, permission and build tests; it cannot replace those two local evidence checks.

A Windows exclusive file lock protects the desktop configuration directory against concurrent processes using the same refresh token. Debug IPC smoke tests can point `FARSAIL_TEST_PROFILE_DIR` to an isolated temporary directory. Stop test services with `scripts/test-coordinator.ps1 -Stop`; it affects only the `farsail-dev` project and retains data volumes and the ignored `.local/dev.env`. Public services, a second Windows computer, cross-NAT operation, physical mobile devices and the secure desktop were not verified in WI-004.

The current [file baseline](FILES.md) uses `Session::send/receive`, the `File` channel, independent `files` grants and the local `can_files` switch. File connections always require manual approval, including same-account remote standby. They do not start capture/input or inherit screen permission; receiving files is off by default. Resumption is not implemented.

## 0.1.2 separate window and recovery

Viewing/control opens in a separate native window. Closing it ends only that session; the main device-management window remains. Clicking the screen gives it keyboard focus; focus loss, disconnection or stopping cancels queued input. The ended state clears the old screen and displays the reason in Chinese. Media/network timeouts can automatically attempt at most 3 fresh authorization requests; closing the window cancels at any time. Authorization denial, revocation, expiry and legacy closure with an unknown reason retain the ended state. The actual selected P2P/relay path and RTT are continuously displayed; path migration does not mean reconnection. This version is compatible with the released server and does not require redeployment. For validation and limitations, see [WI-REMOTE-012](verification/WI-REMOTE-012.md).
