# Accessibility screenshot sharing

Date: 2026-11-04. Baseline: `b427d00`. Ordinary-install candidate: `0.1.9-a11y-preview2`, code 10. No public channel release.

## Mechanism and choice

On Android 11+, the user may select `AccessibilityService.takeScreenshot`, with `canTakeScreenshot` declared in service metadata. System projection remains the default. The user explicitly chooses screenshots after reading capture, battery and protected-page information, then grants system accessibility access if needed. Capture targets a 350 ms cadence including capture/copy/encoding, adapting down on system rate limits; hosting is advertised only after a successful frame. An independently stoppable `connectedDevice` foreground task provides notification controls without creating a `mediaProjection` session. Reference: [accessibility screenshot API](<https://developer.android.com/reference/android/accessibilityservice/AccessibilityService#takeScreenshot(int,%20java.util.concurrent.Executor,%20android.accessibilityservice.AccessibilityService.TakeScreenshotCallback)>).

The selected method and sharing choice are scoped to the server/device. Accessibility alone neither starts sharing nor approves connections; direct control requires its separate choice. Sign-out, explicit Stop and identity changes cannot restore old intent. Permission revocation stops capture and invalidates local capability immediately; foreground return after permission recovery may retry. Screenshot restoration has no projection-consent dialog.

Hardware screenshots are copied to software RGBA, bounded to a 2560-pixel longest edge and passed through native full-resolution JPEG 4:4:4 encoding. Capture epoch and geometry are checked atomically at publication, so late frames cannot resize a new capture or publish into a new identity. Hardware buffers are always closed; late callbacks and stopped frames are rejected. The existing system-projection path is retained.

Screen wake uses ordinary window APIs through a non-exported entry that rechecks screenshot sharing, accessibility and the current native control session’s capture/layout epochs. The first action wakes without replaying coordinates; the window exits automatically without requesting dismissal of a password lock. View-only permission cannot enter this path.

The `onInterrupt` callback interrupts accessibility feedback rather than revoking permission. It clears gestures without suspending valid control/capture; actual permission loss and unbinding still revoke capability. Reference: [accessibility service lifecycle](https://developer.android.com/reference/android/accessibilityservice/AccessibilityService#onInterrupt()).

## Boundaries

Screenshot capability does not bypass device passwords or protected pages. Vendor app stops and network restrictions may still interrupt service; adding this backend does not turn the earlier physical-device failure after power exemption into a pass. Android 8–10 retain system projection. Physical vendor compatibility, prolonged unplugged operation, remote input on the lock screen and production release are separate checks, without a pass claim before verification.


## Physical latency follow-up

The user clarified that USB removal was intentional and sharing was not explicitly stopped. On reconnection at 15:39:51, the phone was noninteractive with active screenshot frames and current heartbeats; this single snapshot does not prove uninterrupted service during the entire unplugged window. At 15:40:51 a screenshot exception stopped capture while heartbeats continued. Exact system error logging was added; the original generic exception cannot establish its cause.

The user reported over one second of perceived delay on the same network with desktop 0.1.34, and declined a temporary system-projection comparison. The capture method remains unchanged. Read-only local diagnostics on the physical device showed direct transport, 12–48 ms network RTT, 24–122 ms cumulative frame confirmation, 0–5 ms local sending, 0–9 ms publication-to-send wait and 2–13 ms input queueing across twelve samples. These are component samples, not measured screen-to-screen latency or proof of the full root cause. Frame payloads were 88,786–287,520 bytes; original full-resolution quality was retained. Source: `.local/android-latency-20261104/physical-media-window.json`.

Identical newly obtained RGBA screenshots now reuse the previous JPEG after exact meaningful-row comparison; changed pixels, dimensions and invalid buffers cannot use the cache. Pixel/JPEG state is cleared on local capture stop and fenced by the current epoch. Successful cached frames still receive fresh sequence numbers. Temporary screenshot rate limits now gradually recover toward 350 ms after stable operation, rather than permanently retaining the slower interval. This reduces repeated work and prevents persistent backoff; it does not turn screenshot mode into high-frame-rate projection.

[AOSP request throttling](https://android.googlesource.com/platform/frameworks/base/+/main/core/java/android/accessibilityservice/AccessibilityService.java) defines a 333 ms minimum interval. Screenshot result age, encoding, sending and cumulative ACK age are independent of final WebView presentation time; diagnostics expose no identities, addresses, input payloads or credentials. Candidate `0.1.9-a11y-preview4` is a local ordinary-install optimization build; actual physical comparisons and regression outcomes are recorded in `.local/android-latency-20261104/verification.json`. Public feeds are unchanged.


Final checks passed: 18 Rust tests, Clippy, 7 JVM tests, debug/release builds and lint, signature and dual-ABI/16 KB packaging. On the physical device, native processing of unchanged screenshots fell from about 50 ms to 1–3 ms; changed frames still took about 55 ms, preserving dimensions and quality. No percentage improvement in final screen-to-screen delay was measured. Samples are in `.local/android-latency-20261104/physical-preview3-samples.json`, with direct transport re-established at the end; later noninteractive direct samples still advanced frames and ACKs.

The first regression attempt failed to find its target UI. After clearing only the owned emulator's synthetic state, exiting secure lock reproduced a missing system screenshot callback. Each request now has its own generation: timeout invalidates the old request before at most two retries while actual accessibility permission remains valid. A late success closes its buffer without cancelling the newer timeout; actual revocation and other error codes still stop capture. The subsequent real screenshot/rotation/secure-lock/revocation-restoration/explicit-stop lifecycle case passed, with an observed timeout retry followed by advancing frames. Failure and final pass evidence are `.local/android-latency-20261104/screenshot-lifecycle-clean.log` and `.local/android-latency-20261104/screenshot-lifecycle-retry.log`. Recovery is bounded and does not guarantee uninterrupted capture under every vendor policy.
