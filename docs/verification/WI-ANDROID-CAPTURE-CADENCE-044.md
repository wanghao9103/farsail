# Android capture cadence and accelerated JPEG

2026-11-06. Investigation found an explicit 100 ms projection admission interval and the portable JPEG encoder's AVX2-only SIMD support. On one connected ARM phone, a 48-second observation produced 8.37 frames/s; combined scaling/encoding had a 48 ms median and 77 ms p95. This is an observation of one device and workload, not a controlled encoder benchmark or a diagnosis of every stalled session.

The candidate uses statically bundled libjpeg-turbo on Android, retaining 4:4:4 sampling at quality 80–90, existing geometry checks, byte limits and protocol. A thread-local compressor avoids repeated initialization. Other platforms keep their existing encoder. Projection admission targets 30 FPS, tolerates small display-clock jitter, resets on surface replacement and avoids catch-up bursts after slow encoding. It still acquires only the latest buffer; the existing demand gates and bounded media sender remain in place. Capture cadence and conversion/JPEG timings are exposed by the existing local diagnostics.

Local validation: 25 Android Rust and 10 media tests passed, as did all-target Clippy, formatting and shell syntax checks. All 12 JVM tests passed, including three new cadence cases. A Windows Unicode-path test-class loading failure was reproduced for all test classes; the same sources passed from an ASCII temporary directory. These host tests do not execute the Android-specific native encoder. CI produces a separate ARM media test executable so color/geometry/size checks and a short synthetic comparison can run on the connected phone before installing the APK.

The signed candidate from `4f12158` built successfully. All 10 native media tests passed on the connected ARM phone, including full-color sampling, geometry and byte limits. An explicit synthetic 1088×502, quality-80 comparison encoded five identical inputs per backend: the portable encoder took 177,291 µs total; the accelerated encoder took 67,527 µs. Outputs were 568,032 and 568,248 bytes. This measures only JPEG encoding of synthetic pixels in the shell test process; it is not game capture, scaling, delivery, display FPS or an application-level speedup. The package retains the installed certificate and was verified before a single-phone trial update. The documentation language-switch check was fixed locally and passes for all 71 document pairs.

Pending: post-update real-device capture measurements and five-window acceptance. Neither 30 displayed FPS nor a complete fix for reconnects is claimed. The current candidate does not change the accessibility screenshot cadence, the server or public update feeds.

Follow-up: the phone UI now displays its own short device ID separately from the other-device list. Local diagnostics whitelist the bound ID, capture/hosting flags and session ID; they do not include access tokens or passwords. `sent` remains the latest frame sequence for compatibility; the new `sentFrames` counts completed media sends. A sequence delta must not be treated as transmitted FPS when unpublished or overwritten frames create gaps. The original 8.37 FPS baseline is a publication rate; its sampled `sent` delta is not a send count. The connected trial phone and desktop target must be matched by actual device ID before accepting performance measurements.

2026-11-07 follow-up: five independent physical desktop sessions were observed using direct paths. A 52-second sample of another connected phone on the original encoder produced 8.37 published FPS, median encode time 56 ms, median RTT 95 ms and median application ACK 343 ms. These measurements are not presented FPS. The first trial handset was rolled back without clearing its data after a reported sharing failure; rollback did not restore sharing, and the cause remains unconfirmed. Its physical USB association was confirmed, but the earlier device-name inference remains unverified. Further UI changes resolve the registered local name by its actual ID on home and sharing pages; the separate name-only branch retains the original native implementation.

The experimental sender now permits the existing two bounded slots to overlap only when delivery ACKs, write duration and RTT indicate a healthy path. Queueing immediately restores single-flight waiting; the 15-second no-progress deadline and bounded stalled-frame probe remain. Local diagnostics expose `overlapAllowed`. A five-session synthetic comparison used 1088×502 pre-encoded images, a 30 FPS source and a controlled 50 ms receiver ACK delay. Original single-flight delivery achieved 11.97–12.10 FPS per stream, 142.71 Mbit/s total payload and maximum stream p95 frame age 68 ms. Adaptive overlap achieved 15.60–15.73 FPS, 178.19 Mbit/s and 89 ms respectively; neither run closed a session. Quality feedback ranges differed (80–90 versus 80), so this is not a fixed-quality codec benchmark. More throughput consumed more bandwidth and increased frame age. The comparison excludes capture, encoding, WebView decode/paint and real Wi-Fi contention, and does not prove a five-phone improvement. The isolated CI link additionally tests five 1088-pixel streams sharing 35 Mbit/s for 120 seconds, requiring sessions to stay open and p95 native frame age at most 1500 ms; that bound is a congestion check, not a smooth-play target. Candidate label: `0.1.14-perf3`; no public release yet.
