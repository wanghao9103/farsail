# Remembered Android access — 0.1.4

The control choice existed only in native runtime memory and capture consent ended with the process. The app now persists intent for the authenticated server/device, restores allowed control when accessibility really connects, and requests a new visible system capture authorization when reopening the foreground home page after capture ended. A live share is retained. Nothing replays a capture token or grants system accessibility permission.

App/notification stop and recording cancellation clear sharing intent; sign-out clears both. Control revisions prevent a delayed restore from overriding a newer disable; consumed recording request generations and device/server scope prevent stale consent from restarting a stopped or different-device share. Settings can turn off foreground sharing restoration.

Local Kotlin/APK/lint and owned API 35 acceptance passed for actual process replacement by the same-certificate APK, private preference retention without credentials, restored native control, no automatic background recording restart or consent prompt, a fresh foreground system dialog, cancellation without a loop, explicit stop across another replacement, stale restore/consent, foreign-device denial and clearing on sign-out. Phase 1 is deliberately terminated while a real share is live; its crash marker is the expected handoff, not a passing JUnit test. Normal-process UI and state are verified externally; the separate intent-guard test passes normally.

The debug-only read-only state provider requires shell DUMP permission and an emulator. It is excluded from release variants, and publication rejects it in the release manifest. API 36 emulator System UI ANR and crash/force-stop accessibility binding gaps were observed in separate attempts; they are not counted as successful acceptance or resolved by changing system permissions in production. Physical OEM background policy and force-stop service recovery remain outside the verified scope.

## Authorization-time persistence — 0.1.8

The previous implementation saved control only after accessibility connected. An initial enable that opened system settings could be lost if the process disappeared there; successful previously saved choices were already retained. Both the switch and setup action now persist intent before leaving the app. Sharing intent is likewise persisted before system consent. Initialization publishes authenticated state and readiness together; a positive recording result waits in Activity memory until that snapshot is ready, with the existing generation and identity checks preserved. Cancellation, Stop and sign-out still revoke the relevant choice. The home page explicitly distinguishes remembered intent awaiting restoration from live capture.

The owned API 35 access-choice driver passed saving control before permission, actual same-certificate process replacement with permission absent, automatic control activation after service connection, a real positive recording grant delayed until account readiness, and Stop rejecting the deferred grant. Evidence: `.local/android-choice-verification/attempt-1793679415645304676/verification.json`. Early attempts exposed test gesture timing and an emulator attach failure; they are not counted as product acceptance. The process-replacement handoff remains an expected instrumentation termination, separately verified by the new process state.

The original normal-process memory regression also passed for 0.1.8: live sharing before replacement, restored control, fresh foreground consent, cancellation without a loop, explicit Stop across another restart, stale-generation denial, device scope and logout. Evidence: `.local/android-memory-verification/attempt-1793679626021029139/verification.json`. Its fixture now waits for a real accessibility unbind before rebinding and scrolls controls into a stable viewport; no production system permission is changed. Debug build, Kotlin unit tests and lint passed.

Host NativeSmokeTest returned OK (4 tests), with the API 36-only secure-lock case assumed on API 35. The real JNI/QUIC mobile controller regression also passed against synthetic desktop/phone peers, including static-frame control, rotated touch, text, view-only rejection, background close and pending cancellation. Evidence: `.local/android-choice-native-regression.log` and `.local/android-controller-verification/attempt-1793679803317677371/verification.json`. The test waits for device-list refresh before using its controls; the initial stale accessibility-node failure was test synchronization, not accepted product behavior.
