# Windows multi-view frame delivery and lease retries

2026-11-07. This investigation separates native reception, local UI delivery, JPEG decoding and phone/network performance. The user's five direct sessions were available, but a desktop trace captured a `renewal_failed` closure. Its underlying HTTP status was not recorded, so a specific server failure is not claimed.

On one Windows machine, an isolated native WebView2 fixture generated 1088×502 full-color JPEG frames from a continuous 30 FPS clock. One window using the existing image renderer submitted about 30 FPS; five simultaneous windows submitted approximately 15 FPS each. Later ordinary-IPC samples submitted about 11–12 FPS with local retrieval medians around 60 ms. Other applications and the user's existing remote windows remained running, so these are observations under that workload, not an exclusive hardware benchmark. Submission means updating the decoded image source, not physical monitor paint or phone-to-screen latency.

Replacing only the image renderer with Canvas, including an ImageBitmap experiment, did not improve the workload. Those production changes were removed. The retained implementation keeps the original image renderer and transfers Windows frame bytes using WebView2 read-only shared buffers. Both the initial request and delivery after an asynchronous frame wait enforce window/session ownership. Each viewer has one outstanding read, a request/session-matched receiver, explicit cancellation and buffer release. Native mappings close immediately after posting; script mappings release after consuming the frame. Unknown, stale and cancelled events release their owned buffers. Unsupported runtimes or a missing delivery fall back to the existing binary IPC. No new authentication or media protocol is introduced. See [Microsoft's shared-buffer lifetime contract](https://learn.microsoft.com/en-us/microsoft-edge/webview2/reference/win32/icorewebview2sharedbuffer).

The first shared-buffer five-window observation submitted 21.90–23.74 FPS per view, with retrieval medians 19.3–20.8 ms. Final same-binary controls measured forced binary IPC at 10.95–11.50 FPS (retrieval median 66.0–69.1 ms), versus shared delivery at 20.30–21.50 FPS (19.0–21.5 ms). Deliberately delaying the first decoder by 200 ms reduced only that view to 4.05 FPS; the other four submitted 25.15–26.15 FPS. All shared reports confirmed shared delivery. This removes a measured desktop bottleneck, but does not prove that five real phones now display at that rate. Android capture admission and wireless JPEG capacity remain separate limits.

Local frame-reader tests cover cross-session matching, independent viewers, late delivery after cancellation, exact buffer release, unsupported and empty reads, authorization errors, and bounded fallback after a missing reply. Native fixtures use an isolated profile and synthetic pixels. Their explicit Debug-only build option uses an unelevated test manifest; production privilege settings are unchanged.

Lease checks previously converted every HTTP/network error to rejection and stopped the host on the first failed check. Retryable coordinator/network failures are now distinct from identity, permission and malformed-proof rejection. Error HTTP status is preserved without reading unused gateway error pages; successful proof responses retain their size limit. Retries use the existing verified deadline, never extending it on failure. An issued token is retained until its peer acknowledges it; a temporary peer check can request retry. Explicit denial and the independent expiry gate remain terminal. This is compatible on healthy connections with older clients; full transient-failure handling requires both endpoints to be updated.

The five-real-QUIC-session fault-injection test passed without reconnecting after temporary check, issue and peer-check failures. The sustained-outage test closed at the last verified deadline without extending it. The full client suite (58 tests) and transport suite (22 tests) passed locally, including revocation, identity and expiry cases. Desktop tests (68), frontend policy/reader tests (36), the full browser regression and native window/session scope checks also passed. Android home/sharing also display the registered local name and short ID from the separate name-only change.

An Android regression initially timed out during the four-window first-frame check. Its fixture performed four synchronous encodes on the same current-thread runtime; diagnostic repeats measured the first frame already 430–591 ms old before polling transport, close to the unchanged 700 ms freshness gate. The fixture now encodes on blocking workers, while CI runs separate timed scenarios serially to avoid unrelated workload contention. Every four-host scenario still runs its four connections concurrently. The complete local Android suite then passed (25 passed, two opt-in bandwidth tests ignored); production timers and freshness limits were not changed.

Candidate identifiers are Windows `0.1.43-rc.1` and Android `0.1.14-lease1`. Real five-phone post-install acceptance is pending. No formal update feed or coordinator deployment is changed by this work.
