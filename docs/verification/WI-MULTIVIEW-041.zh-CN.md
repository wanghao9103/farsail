# 一台控制端连接四、五台安卓目标

日期：2026-11-05。产品基线：桌面 0.1.36 / 安卓 0.1.12。证据：`.local/four-five-phones-20261105/`。

## 结果

四路、五路均通过不同账号和全部设备同账号两种场景。一台真实 NativeClient 控制端通过本地 HTTP 协调服务、隔离的 PostgreSQL schema 和真实认证加密 QUIC，连接四 / 五个独立安卓协议模拟目标。每路收发 64 KiB 媒体包与带路由标记的控制包，持续约 81 秒并跨越租约轮换。重启、最后关闭其中一路后，其余会话保持连接，额外重连为零。同账号四 / 五路分别交换 2,732 / 3,290 个包，媒体总量 179,044,352 / 215,613,440 字节。报告：`fanout-4-same-account.json`、`fanout-5-same-account.json`；不同账号报告无后缀。

Chromium 标签用例分别通过 60 次切换和仅 A 路的六次恢复，同时让 B 路状态查询延迟 1,800 ms；每会话最大在途状态查询为一，输入没有串设备。四 / 五个独立可见窗口也通过：故意阻塞 A 的解码不会停止其他窗口，A 的重连和关闭不会影响其余设备，标记输入仅到指定目标。报告位于 `4/`、`5/` 的 `tabs-result.json`、`windows-result.json`。

原协调服务集成和新增不同账号用例一起运行，3 项通过；同账号用例另行一起运行，2 项通过。客户端集成 Clippy 禁止警告、工作区格式与 diff 检查通过。

## 边界

安卓设备元数据、媒体内容和前端 IPC 为模拟。真实协调服务 / 传输与真实前端渲染分开验证，不等于五台实体手机端到端验收；没有测量安卓采集、实体解码 / GPU / 温度、游戏帧率、跨网或整夜保活。浏览器夹具约 6.4 帧 / 秒由 150 ms 合成源间隔决定，不能当作真机性能。没有使用生产协调服务或真实系统输入。

可复用原生测试位于 `crates/client/tests/coordinator_flow.rs`，需要 `FARSAIL_TEST_DATABASE_URL`，可通过 `FARSAIL_FANOUT_REPORT_DIR` 输出 JSON。未设置数据库时明确跳过执行。参见[查看器行为](WI-VIEWER-TABS-039.zh-CN.md)。

### 旧版采集节奏的源码边界

App 0.1.12 的普通录屏通道在 `CaptureService.kt` 中丢弃距离前次不足 100 ms 的帧，即编码前最多约 10 FPS；免重复录屏确认的辅助功能截图通道在 `AccessibilityFrames.kt` 中以 350 ms 起步，并在被系统限频后退避，名义上最多约 2.86 FPS。两者都不由 Wi-Fi 速度决定，也不等于实测每台手机必达该帧率。本轮不知道昨天每台设备实际使用哪个通道；10 FPS 的协议源与 30 FPS 的前端强压源都不能替代真机采集 / 编码测量。

### 源码发现与剩余边界

`viewer::sync_visibility` 与前端 active 目前只使用标签是否 selected，未结合原生窗口最小化；最小化独立窗口后应用层仍请求视频，是可定位的资源节省遗漏。本轮未修改该行为，也未测系统最小化后 WebView2 节流，不能将它认定为昨天四个窗口的根因。审查未发现跨会话的应用层全局解码队列；原生最新帧覆盖与 ACK 独立于前端显示。`frame_age_ms` 日志仅为距最近 native 收图的时间，received / delivered 也不是唯一显示帧数。指标起终点及源码定位见 `metrics-audit.md`。

常规安卓库回归 23 passed / 2 ignored；两个 ignored 用例分别实际执行：原严格四路 35 Mbps 验收通过（native 约 0.4 FPS，auto 8.05–8.97 FPS），新 matrix 在 35 / 20 Mbps 和不限速三种条件完成。原 7 FPS、两倍改善、700 ms 年龄与 220 ms RTT 门槛保留；all-target Clippy 禁止警告、Rust 格式与 70 对双语文档检查通过。

网络和前端是分层模拟，不能相加或拼成五台实体手机端到端 30 FPS 证明。未覆盖实际手机采集 / 温度、Wi-Fi 无线争用、Windows 硬件 WebView2、游戏现场或整夜运行。按窗口像素发送的完整机制要求桌面 0.1.42 与安卓 App 0.1.14；未升级的 0.1.12 不能套用本轮新协议结果。现网采集恢复与正式发布另见[采集恢复补证](WI-CAPTURE-RECOVERY-043.zh-CN.md)。本轮保持部分验证，不发布测试专用的新安装包。

## 可见多窗口的逐帧渲染修复

后续继续排查基线 `216072b`：每张 JPEG 解码完成都会 `setPicture`，使整套 Viewer 工具栏、菜单与输入组件跟随帧率重新执行；四 / 五个可见窗口会累加这项开销。现在 `sameFrameGeometry` 检查显示器、布局代次及尺寸，只有这些值变化才更新 React 的画面状态；同几何的新像素通过当前图像节点更新。仍先完成解码及活跃 / 选屏门禁检查，随后才显示新图，没有改画质、帧率来源、网络预算或授权。

图像挂载及无关界面刷新统一从最新 URL 引用恢复，避免重新使用已撤销的元数据帧 URL；React 不再声明旧图片 src。尺寸 / 布局变化仍与输入处理器一起提交，输入坐标、旋转和断线清理继续使用已有门禁。新增 `UI_ONLY_FRAME_HOTPATH` 专项：一路解码等待不堆积或阻塞另一页，解码完成后确实更新；停止合成新帧并等待状态 / FPS 刷新后，最新图像仍可用，没有回退旧 URL。

最终生产构建、Chromium / WebKit 完整查看器回归和两个引擎的上述专项通过。证据 `.local/multiview-render-fix-20261106/` 中的 build-final、viewer-_-final 和 hotpath-_ 日志。初次外部订阅方案在压力测试中变慢，已舍弃；初轮 profiler 缺少观察变量导致报错，其失败记录保留。启动期解码并发的旧夹具断言失败与正式测量区间分开审计，不放宽门槛。

性能对照使用五个可见的独立页面、相同变化纹理 JPEG 与 30 FPS 合成源，统计主线程 JavaScript 执行时间；它不是整机 CPU 利用率。输入回调身份变化只作为每个 rAF 观测到的父组件更新代理，不能当作完整提交次数。不同 Chrome 版本的数据不混作受控前后比较；正式统计保留浏览器版本、源文件摘要与原始日志。不存在用户 Wi-Fi 测量或实体安卓采集 / 编码，仍有软件 JPEG 解码、合成及长尾等待，不能声称五台实体手机卡顿已全部解决。本轮源码尚未作为新安装包发布。

同 Chrome 157.0.8103.38 的五路观察中，修复前 / 同热路径候选的主线程 JavaScript 累计耗时为 41.54 / 11.11 秒，下降约 73.26%；每个窗口观测到的输入回调更新由 417–476 降至 66–68。正式出帧区间为 20 秒，CDP 快照还包含开始前约一秒，两组采用相同采集逻辑；该比例不能解释为整机 CPU 下降。每路解码从 18.60–21.40 到 20.70–23.15 FPS，p95 并非每路都改善。报告 `comparison.json` 保留这组观察，未将后续不同负载样本拼接成更大的收益。

最终源码另跑同版五路、720×1600、30 FPS 源、20 秒专项：A 注入解码等待后为 27.04 FPS，其余为 29.49–29.64 FPS，均持续更新且输入不串路。软件渲染及宿主负载仍影响绝对帧率，不把该后续样本和前一组基线直接算作提升比例。最终与基线原始报告中的全生命周期解码并发二仍保留为 failed；`formal-concurrency.json` 从原始区间独立重建，所有正式区间并发至多一，未放宽门槛。完整回归和最新帧专项均为实际通过，性能与实体现场覆盖总体保持部分验证。

## 不匹配缓存帧导致运行线程空转

进一步发现安卓 `send_frames` 在缓存 JPEG 的几何 / 布局或当前会话不匹配时直接 continue，绕过循环底部的异步等待。若该拒绝值持续保留，会反复读取同一值，占满一个运行线程；其他任务可能因此延迟。新分支等待 frames / ACK / demand 变化、连接关闭或 50 ms 的后备唤醒，不丢掉同时到来的新帧，也不重新建立会话。

新增单线程真实认证 QUIC 回归 `stale_cached_geometry_yields_to_runtime_timers`，注入一张与当前布局不符的有效 JPEG。旧实现在外部 8 秒 timeout 下退出 124，内部 200 ms 定时器无法执行；修复后定时器正常返回，随后发布有效帧并在同一连接收到当前布局，确认恢复没有依赖断线重连。最终安卓库 24 passed / 2 ignored、all-target Clippy 禁止警告与格式检查通过。证据 `.local/stale-frame-yield-20261106/`。

这是故障注入证明的错误分支，不是现场抓到的布局异常；普通窗口协商本来会清空旧帧，不能断言每次旋转都会触发空转，或把它认定为用户所有可见窗口卡顿的唯一根因。没有改变编码、截图间隔、网络预算、授权或公开安装包。

## 几何提交与结束帧生命周期复查

继续检查未发布的快速画面更新，复现一个并发边界：新帧先更新请求中的几何引用，React 却可能尚未提交相应输入处理器；第二张同几何帧会提前更新像素。测试暂停 React 的排队工作，解码两帧 450×800 图片：旧实现显示新尺寸时输入回调仍是旧版本。现在仅在几何变化 / 首次挂载时用 `flushSync` 一起提交画面及输入处理器，同几何帧仍使用原快速路径。专项还增加布局代次变化，确认点击携带当前布局。

另复现输入发送失败后的结束状态缺口：暂停一个解码，强制输入 RPC 失败，同时不完成原生关闭请求；释放解码后，旧实现会把已清空的画面再次显示。现在用独立的媒体运行标记立即停读、使旧帧失效，并清除正在解码图像的来源及未发布 URL。该标记与窗口生命周期分开，手动重连仍使用原窗口 lease。原生结束与组件卸载也统一清理。新增回归要求在关闭 RPC 仍未完成时就撤销待解码 URL，随后解码完成不能恢复画面或产生新媒体读取。

JPEG 部分改用 `subarray` 视图交给 Blob，去掉每帧一次载荷大小的中间复制；Blob 的内容及全部字节边界不变，没有单独量化此项 CPU 或时延收益。对照证据 `.local/frame-geometry-20261106/`：before / after 是几何原子性故障注入，late-before / late-after 是关闭等待期间迟到解码故障注入；失败日志与 JSON 保留。

这些是发版前源码审查与合成 IPC 复现，不是用户实体四手机上的问题捕获；未测 Wi-Fi，无新的整机帧率或延迟保证。复查还覆盖捕获 epoch / profile 拒绝、暂停 / 恢复、重连组件身份、按键布局归属与资源清理，没有据猜测修改其他协议或采集节奏。

最终生产构建、Chromium / WebKit 完整查看器回归和包含上述故障注入的双引擎专项通过；状态策略 30 项通过。最终日志为 build-terminal、final-chromium、final-webkit、terminal-chromium、terminal-webkit、policies-final。复查所覆盖的远程画面 / 输入 / 生命周期路径中未再发现新的可复现缺陷，不代表实体设备、无线环境或软件全局无 Bug；没有发布新安装包。

## JPEG 大小上限的完整回退

继续复查安卓 `encode_rgba_profile` 时，确定性 1080×2560 高熵 RGBA 测试复现了丢图：Q90 / Q85 超出限制后旧代码返回 None，但 Q80 可编码为 3,855,888 字节，低于原 4,000,000 字节上限。现在按现有 80–90 质量范围最多尝试三次，直至合法最低质量；不会降到 80 以下，不改变全色 4:4:4、像素尺寸或大小预算。所有合法质量仍超限时继续拒绝。

回归 `oversized_native_frame_retries_the_supported_quality_floor` 在旧实现实际失败；修复后逐字节匹配合法 Q80 参照，尺寸仍为 1080×2560。最终安卓库 25 passed / 2 ignored、all-target Clippy 禁止警告和格式检查通过。证据 `.local/jpeg-fallback-20261106/`，仅是合成内容的编码复现，不代表已定位用户手机现场，也没有单独量化最坏三次编码的手机 CPU 成本。普通一次就成功的帧不增加尝试，截图缓存仍可复用静止画面。

## 帧头整数范围与重复读取

帧头的序号和布局是 u64，而桌面 IPC 游标 / 输入使用 JavaScript number。注入序号 9007199254740993 时，旧界面将其舍入为 9007199254740992；原生最新序号仍大于舍入后的游标，可能反复返回同一帧，而 UI 又因舍入后的序号未增加而跳过。旧版浏览器复现确认注入五次后仍未关闭，画面仍存在。这里是异常语义数据，不是实际 Wi-Fi 吞吐或无线误码测量。

现于分配 JPEG Blob 和推进游标之前拒绝非安全整数序号 / 布局以及非正序号，明确结束当前画面并请求关闭本会话，避免不精确输入布局和重复读取；正常范围与原生 u64 协议本身未改。双引擎专项分别覆盖序号与布局越界，要求只注入一帧、只关闭一次、停止后续读取，原页面仍可见。修复后本地对照只收到一次异常帧即关闭并清图。证据 `.local/frame-counter-20261106/`，不是说明正常手机短期运行会到达该序号。

### 追加：等待显示器列表时避免重复复制缓存帧

恢复中的查看器将显示器列表延迟 1.8 秒，在 600 毫秒观察期内四次取回暂时不能显示的同一缓存帧。接收循环现在对仅由状态或选屏推进的阶段（`waiting_list`、`unavailable`、`selecting`）在 IPC 前等待；`awaiting_frame` 仍正常取帧，不推进缓存游标、不暂停原生收包与 ACK。同一探针修复后等待期读取零次，列表返回后仍成功显示唯一的静止缓存帧。证据：`.local/frame-wait-20261106/{before,after}.json`；完整回归的两个静止恢复用例（含选屏回复延迟）均加入此断言。这消除了重复复制，不能当作用户实际 Wi-Fi 延迟的测量结论。
